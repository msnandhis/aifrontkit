# Contribution and governance

## Contribution types

Contributors may propose schemas, runtime capabilities, framework bindings, adapters, primitives/components, patterns, registry items, themes, fixtures, documentation, and translations. Each type has an owner/reviewer group and definition of done.

## Decision process

Small compatible changes use normal review. New public contracts, extension points, dependencies, registry types, or architecture boundary changes require an RFC/ADR containing problem, alternatives, compatibility, security/accessibility, migration, and maintenance ownership.

## Maintainer principles

- Protect frontend-only and framework-neutral boundaries.
- Prefer evidence from real use cases over speculative abstraction.
- Require named maintainers for new framework adapters or major integrations.
- Keep official registry quality higher than community catalog breadth.
- Publish conflicts of interest for licensing or marketplace decisions.

## Registry contributions

Official items require full tests, fixtures, docs, provenance, license review, responsive/accessibility coverage, and long-term ownership. Community items use namespaced identity and a distinct trust label. Trademarked product copies and unclear-source assets are rejected.

## Legal prerequisites

Before accepting external contributions, choose a DCO or CLA process consistent with dual-licensing goals, publish a code of conduct and security policy, and document ownership of contributed registry source and media.

## Governance growth

Begin with a small accountable maintainer group. Add public roadmap, RFC log, release ownership, and escalation paths before forming elaborate committees. Commercial priorities may fund OSS work, but public API and security decisions remain documented.
